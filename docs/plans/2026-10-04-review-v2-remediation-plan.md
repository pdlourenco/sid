**Date:** 2026-10-04
**Source:** [`docs/analyses/2026-10-04-repo-wide-review-v2.md`](../analyses/2026-10-04-repo-wide-review-v2.md) (anchored at `1785dd3`). Finding ids below (`§3.2`, `F1`, `U1`, `K3`, …) refer to that document; `C1`–`C5` are this plan's Phase-C items.

The ordering principle is the same as the July plan's, with one addition learned from this cycle: **repair the gates before adding the tests that rely on them** (Phase A), because the July remediation added 10 cross-vectors and ~120 tests into an infrastructure that, as §4.1 shows, could not have rejected several of the errors it was meant to catch.

### 0.1 Must-do set (the cut line)

The inventory is a backlog, not a release gate. The **must-do set** is the gate repairs plus the critical defects. It does **not** remove every silent wrong answer: F3 (D3), F4 (D4: MATLAB ETFE's `max(PhiV, 0)` turns NaN into 0), F12 (D6), U2 (D5), F8/F9 (D9), K1–K4 (D10) and the SP8 Welch `σ_G` understatement (E1b) form the **first backlog tier**, scheduled as soon as their §0.2 decisions are made (K4 needs none). (Pulling them into the set instead is the maintainer's alternative; it raises the set's decision count accordingly.) Decision-free items outside the set may run alongside it.

| Item | Why it is in the set |
|---|---|
| A1, A2, A3, A4, A5, A6, A8 | without them the gates cannot reject the errors they exist for (§4.1, §4.2); A5 is in the set because A6 depends on it (plan §9) |
| A10 | the documented Octave floor has no CI backing (§4.2); F1 item 1 depends on it |
| D1, D2 | crashes / silent truncation on documented input (analysis §5.1 F1, F2; §5.3 U1, U5); D1 needs no decision, D2 needs the §14.5 additions accepted |
| B1 | the one test relaxed to absorb a bug and never restored (§3.2) |
| F1 item 1 | the install page states a platform floor no other source and no CI job backs (§7 item 1; final wording follows the A10 decision) |

The must-do set needs seven decision items from §0.2 (A1; A2 — three rows: policy, who commits, provenance check; A3; A6; A10; D2; and E1b's IO `Cost` row, which A6 depends on); D1, A8 and B1 can start immediately, A1 once its ADR is accepted, and A4/A5 as soon as A3 is decided (§9: A3 ──► A4 A5 ──► A6). A7 is deliberately outside the set: until it lands, **nothing catches a vector both ports match wrongly** (ADR-0001's stated gap), so the must-do set makes the gates bite on port disagreement only.

## 10. Execution environment — what a cloud session can do, what needs local MATLAB, what needs the maintainer

Three environments:

- **CLOUD** — a Claude Code cloud session: Python and everything pip-installable (numpy/scipy/pytest/matplotlib/nbmake, ruff, MISS_HIT, mkdocs), git + GitHub, Chromium/Playwright, apt **GNU Octave 8.4** (below the documented 11+ floor). **No MATLAB, no toolboxes, no release secrets, no PyPI credentials.** Ruleset application and release creation are technically reachable (the session identity is the admin owner) but are maintainer-only by governance (CLAUDE.md §4–§5).
- **LOCAL** — the maintainer's machine: MATLAB R2024a with System Identification + Signal Processing toolboxes, Python, Octave, admin rights.
- **PR CI** — on any PR touching `matlab/`, `testdata/` or `tests.yml`, MATLAB **R2025a with both toolboxes** (`runAllTests.m`, `runAllExamples.m`, `generate_reference.m` without committing) and **snap Octave 7.1.0** (despite the step name); `cross-validate.yml` runs `validate_reference.m` under the same 7.1.0 plus the Python consumer. Most "needs MATLAB-proper confirmation" items are therefore satisfied by the PR's own checks.

### 10.1 Environment facts that bear on the classification

The executed record is the analysis's Appendix A; only the facts the §10.3 table depends on are kept here.

- **Octave runs the non-plotting suite and the validator in CLOUD** (374/380 cases and 32/32 vectors in the authoring container; 432/432 and 12/12 examples in a fresh one). One authoring container could not render figures (`ft_text_renderer: invalid bounding box`); a fresh one could. Figure-producing items are classed cloud-capable with PR CI as the fallback if that defect reproduces. Plot functions raise their *error* identifiers before creating a figure, so those tests never need rendering.
- **Vector bytes need a MATLAB-proper run.** Octave's `rng`/`randn` stream differs from MATLAB's, so Octave-generated vectors differ at the input level and are not even self-consistent. Generator *logic* can be developed in CLOUD; bytes come from the PR's MATLAB job (pushed to the PR branch under A2 (i-a); uploaded as an artifact for forks, (i-b)), LOCAL R2024a (flagged as churny), or a `workflow_dispatch` of `tests.yml` (only once A2 has removed its push to `main`, or with a no-commit input).
- **Octave `control`/`signal` packages** are not guaranteed in a fresh container: Octave-based Welch/subspace oracles need a `pkg install` first.
- **`scripts/local-ci` prefers Octave** when both engines are on `PATH`: a LOCAL MATLAB-proper run needs `OCTAVE=/nonexistent scripts/local-ci matlab` or a direct `matlab -batch`.
- No job anywhere gives Octave-11 evidence until A10 lands.

### 10.2 Classification vocabulary

- **cloud** — fully developed and verified in a cloud session.
- **cloud-dev → PR-CI** — developed and Octave/Python-verified in the cloud; MATLAB-proper (and snap-Octave) confirmation comes from the PR's own CI jobs before merge; a LOCAL run is optional.
- **local** — cannot be meaningfully done without MATLAB/toolboxes on the author's machine (toolbox functions, engine-specific tolerances, interactive MATLAB-only behaviour).
- **ci-main** — canonical vector bytes from the canonical engine. Today that is the bot commit on `main` after merge; under A2 option (i-a) it is the PR's MATLAB job pushing them to the PR branch before merge (forks: (i-b), the maintainer commits the artifact). Every "ci-main" cell below reads accordingly.
- **maintainer** — admin rights, secrets, credentials, or a `[decision]`; environment-independent.
