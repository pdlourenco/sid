## 1. Phase A — make the gates able to bite

Exit criterion: a deliberate 2×-tolerance mutation of *any* stored field in *any* vector fails both consumers; a regeneration commit cannot land on `main` without both validators running on it; a red test job blocks a normal merge.

1. **A1 — required checks (ADR-0005 amendment).** Add `Octave tests & examples`, `MATLAB tests & examples`, `Tests (Python 3.12)` (one matrix leg), `Validate Python port`, `Validate Octave against MATLAB reference`, and `Build site (strict)` (#199) to `.github/rulesets/main.json`. Three of the six already start on every PR (`tests.yml` and `docs.yml` are unfiltered); the other three live in `cross-validate.yml` and `python-tests.yml`, which are path-filtered — make them always-start with an in-job relevance gate like `tests.yml`, otherwise a required check stays pending on an unrelated PR, which is the exact failure ADR-0005 avoided). Keep the admin bypass. Fix the stale "the required check" comment in `tests.yml`. Four facts to plan around: the app-token mint step precedes the relevance gate (`tests.yml:104–109`), so requiring the MATLAB context blocks every fork PR until the mint is guarded; the `sid-reference-bot` App is an always-bypass actor (`main.json:11–15`), so A1 alone cannot meet this phase's exit criterion — A2 can; `cross-validate.yml` only needs its *workflow-level* `paths:` filter removed (its job-level `dorny/paths-filter` already yields a `skipped` conclusion, which GitHub accepts for a required check), while `python-tests.yml` has no job-level gate and needs one; and because branch protection is already live with `RULESET_TOKEN` configured, the PR-time drift check will go red on the PR that amends `main.json` until the maintainer re-applies the ruleset after merge — not a required context, so it does not block, but the PR description should say so.
2. **A2 — regeneration lands validated (ADR-0002 amendment).** Replace the `[skip ci]` commit with either (a) a bot PR carrying the regenerated vectors, which runs every validator before merge, or (b) a `workflow_run`-triggered validation of the regen commit that reverts it on failure. Make the provenance gate reject `git_sha: "unknown"` and verify the SHA (an ancestor of HEAD under options (ii)/(iii); under (i) see below). Because the relevance gate applies to `pull_request` events only, every push to `main` re-stamps today (docs-only merges included): decouple the provenance SHA from HEAD (stamp the last commit that touched `matlab/`/`testdata/`) or compare payloads before committing. The PR review also reported, via the rulesets API, a second live ruleset named "Main" (id 14923865) that is neither in `main.json` nor drift-checked — confirm it and, if real, bring it under `main.json`. **Reproducibility policy [decision]:** §4.1 F1 shows the pinned R2025a runner is not byte-reproducible (ULP churn in 20 files, 4.5e-5 in `ltv_io`). Options: (i) stop auto-committing — regenerate on PRs, `git diff --exit-code` against the committed vectors *within tolerance* (a numeric diff, not bytes), and commit only on a semantic change; (ii) keep auto-commit but only when a numeric diff exceeds the stored tolerance; (iii) accept churn and drop the README rule. Recommended: (i) — it makes "payloads change only by regeneration" true and kills the provenance-only re-stamp commits. Under (i), **ownership of the canonical bytes** moves to the PR: the PR's MATLAB job (the canonical R2025a engine) uploads the regenerated vectors as a workflow artifact, and when the numeric diff reports a semantic change the PR author commits that artifact's files to the PR branch; the provenance SHA is the commit the generator ran on. Two consequences for the provenance gate: (a) the generator step must check out `github.event.pull_request.head.sha` — the job's default `refs/pull/N/merge` checkout (`tests.yml:111–116`) would stamp a temporary merge commit that never reaches `main`; (b) an *ancestor-of-HEAD* check does not survive squash or rebase merges (all three merge methods are enabled), so under (i) the gate checks that the SHA is a real commit of the repository (fetching `refs/pull/*/head`) rather than an ancestor — unless the maintainer restricts merges to merge commits, in which case the ancestry check stands. A semantic change that arrives without regenerated vectors fails the PR. Closes #204 as a side effect if the bot stops committing on `main`.
3. **A3 — NaN-capable comparison [decision].** `validate_reference.m:340` must treat `NaN`/`Inf` explicitly: equal iff both NaN, or both Inf with the same sign; otherwise fail. On disk, `jsonencode` writes both as `null`; options: (i) encode sentinels as strings (`"NaN"`, `"Inf"`, `"-Inf"`) in `writeJSON` and decode them in both consumers, (ii) store a parallel `<field>_mask`. Recommended: (i) — one convention, readable, and it unblocks degenerate-input vectors (A6/F9). Amend ADR-0002 and `testdata/README.md`.
4. **A4 — Python structural gate.** In `test_cross_validation.py`, replace the per-file hand lists with one loop that asserts every key in `ref["output"]` was compared (a `COMPARED` set per test, checked at teardown), mirroring `validate_reference.m:282–303`; route *every* comparison through `_tol()`, resolve complex keys exactly as Octave does (`<name>_real/_imag` → `<name>_rel/_atol`, and make the generator emit that form for `Phi_xx`/`Phi_xz`/`DFT`), fail on an unknown tolerance key, and compare singular values at full length. Add a `--testdata` pytest option so mutation checks can be first-class (F10) and add three permanent mutation tests (rtol, atol, missing field) against a fixture copy.
5. **A5 — atol floors enforced.** In `generate_reference.m`, a `writeJSON` pre-check that refuses to write any output field whose `min|value| < 1e-12·max|value|` (or that contains an exact zero) without a `<field>_atol`; the same check as a test in both consumers over the committed files. Audit the six default-rtol fields and give them explicit entries.
6. **A6 — the three 1 % vectors.** `reference_ltv_io` already converges (14 iterations; analysis Appendix A) yet drifts 4.5e-5 run-to-run on the canonical engine (F1), so its 1 % is not a convergence problem but an engine-sensitivity one: measure the MATLAB-vs-Python and MATLAB-vs-Octave residuals (the committed bytes are R2025a output, so the Python residual is measurable in a cloud session today: 2.5e-4 on `A`), assert `Iterations < MaxIter` in the generator and store `Iterations` and the `Cost` history, then set the tolerance from the measurement with an atol floor; if the EM path is intrinsically engine-sensitive, pin the per-iteration cost *trajectory* and record the measured drift as the rationale in the generator comment. The `frozen_of_io` generator case (`generate_reference.m:919`) is the one that caps at `MaxIter`: raise its budget or pick a better-conditioned plant so the vector pins a converged iterate. `reference_ltv_cosmic_varlen` is a closed-form solve: 1e-6 rel + 1e-10 atol like `reference_ltv_cosmic`. `reference_frozen_of_io` follows its parent. Add the IO uncertainty fields (`P`, `AStd`, `BStd`) to the IO vector. The analysis §3.1 caveat (the 2026-04-08 "born at 1e-2" row sits at a shallow-clone boundary) is resolved: on a full clone (606 `main` commits) `git log -S` confirms `da5a625` (the only row at the boundary) introduced the `ltv_io` 1e-2. A6 and B4's toolbox files are the only items that need local MATLAB; the maintainer's machine has R2024a, run directly with `matlab -batch` — `scripts/local-ci` prefers Octave when both are installed.
7. **A7 — a third job that needs no port.** `testdata/check_payloads.py` (CI job `Reference payload oracles`): for each vector with an analytic plant (`model_order`, `ltv_frozen`, `lti_freq_io*`, `test_msd`, the new C1 vectors) assert the stored output against the closed form within the spec's own bound; for all vectors assert invariants — coherence ∈ [0, 1], PSD ≥ 0 where the spec guarantees it, `Φ̂_xz = conj(Φ̂_zx)`, `P(k)` symmetric PD, IO `Cost` non-increasing, `util_msd.Ad == expm(A·Ts)`. This is the only mechanism that catches a vector both ports match wrongly (ADR-0001's stated gap). Note: only `reference_test_msd.json` stores its plant parameters; the analytic truths of the other vectors (`A_fr_true`, `A0_true`, `G_mo`, …) exist only inside `generate_reference.m`, so the generator must also write them into each vector's `input`/`truth` block for the oracle job to be port-free.
8. **A8 — no silent skips.** `test_cross_validation.py::_load` raises; `python-tests.yml` drops the `if ls` guard; `validate_reference.m` errors on an empty directory; add a test that the set of `reference_*.json` equals the set the consumers know (closes rule 3 mechanically).
9. **A9 — matrix and hygiene.** Add a `min-deps` leg (`numpy==1.22.*`, `scipy==1.8.*` on Python 3.10 — run once in this review: 414 passed, 1 failed on a 1-ULP `rtol 1e-15, atol 0` tolerance in `test_hann_window`, i.e. the floor is supportable once that tolerance gets an absolute floor; raising the floors instead is a **[decision]**); `filterwarnings = ["error"]` in `pyproject.toml` with explicit `pytest.warns` where a warning is the point; `scripts/local-ci` runs `scripts/check_python_api_pages.py`; fork-PR MATLAB job tolerates a missing App token.
10. **A10 — the Octave floor.** CI's "Install GNU Octave 11.x" step installs snap Octave **7.1.0** (analysis §4.2), so no Octave-11 evidence exists anywhere and the documented 11+ floor is unbacked. Enforce the floor in both Octave jobs (`runAllTests.m` / `validate_reference.m` refuse to run below it, with an explicit override for exploratory runs) and fix the install source (a snap channel that actually carries 11, or another distribution). The floor itself is a **[decision]**: 7.1 and 8.4 are evidently green, so the choice is between lowering the documented floor to what is tested and testing the floor that is documented.

## 2. Phase B — the relaxed, vacuous and over-claiming tests

Exit criterion: every test in §3.4's table either asserts the property its name/docstring claims or is deleted; every tolerance on a deterministic computation is ≤ 1e-8 unless a comment states the measured error and why; no `Verified by:` cites a test that does not assert the rule.

1. **B1** — `test_sidModelOrder.m` Test 5: restore `n_thresh <= 6` (or assert `== 2` on the analytic plant that Test 15 already builds) and delete the `#139` marker.
2. **B2** — calibration: un-gate `TestUncertaintyCampaign` (it runs in about 24 s) instead of adding the repo's first `schedule:` workflow, with the λ grid extended to 1e0 (the point that fails the current gate band on the high side); before re-centring the Python gate band, state in §8.9 (or `uncertainty_derivation.md`) how far above 1 the reported/empirical ratio may sit at mid-λ, so the band pins the spec's expectation rather than the measured 1.07 (principle 3), and fix the stale docstring; make MATLAB Test 13 estimate `Σ` (drop `'NoiseCov', Sigma_true`) and switch it from a per-entry `[0.3, 3.0]` test to a median statistic — per-entry ratios of the *corrected* code reach 1.61 under Octave, so a per-entry band cannot reject the old 1.64 while passing the fix — and add the same mid-λ point. ## 10. Execution environment — what a cloud session can do, what needs local MATLAB, what needs the maintainer

Three environments:

- **CLOUD** — a Claude Code cloud session: Python and everything pip-installable (numpy/scipy/pytest/matplotlib/nbmake, ruff, MISS_HIT, mkdocs), git + GitHub, Chromium/Playwright, apt **GNU Octave 8.4** (below the documented 11+ floor). **No MATLAB, no toolboxes, no release secrets, no PyPI credentials.** Ruleset application and release creation are technically reachable (the session identity is the admin owner) but are maintainer-only by governance (CLAUDE.md §4–§5).
- **LOCAL** — the maintainer's machine: MATLAB R2024a with System Identification + Signal Processing toolboxes, Python, Octave, admin rights.
- **PR CI** — on any PR touching `matlab/`, `testdata/` or `tests.yml`, MATLAB **R2025a with both toolboxes** (`runAllTests.m`, `runAllExamples.m`, `generate_reference.m` without committing) and **snap Octave 7.1.0** (despite the step name); `cross-validate.yml` runs `validate_reference.m` under the same 7.1.0 plus the Python consumer. Most "needs MATLAB-proper confirmation" items are therefore satisfied by the PR's own checks.

### 10.1 Environment facts that bear on the classification

The executed record is the analysis's Appendix A; only the facts the §10.3 table depends on are kept here.

- **Octave runs the non-plotting suite and the validator in CLOUD** (374/380 cases and 32/32 vectors in the authoring container; 432/432 and 12/12 examples in a fresh one). One authoring container could not render figures (`ft_text_renderer: invalid bounding box`); a fresh one could. Figure-producing items are classed cloud-capable with PR CI as the fallback if that defect reproduces. Plot functions raise their *error* identifiers before creating a figure, so those tests never need rendering.
- **Vector bytes need a MATLAB-proper run.** Octave's `rng`/`randn` stream differs from MATLAB's, so Octave-generated vectors differ at the input level and are not even self-consistent. Generator *logic* can be developed in CLOUD; bytes come from the PR's MATLAB job (as an artifact, per A2), LOCAL R2024a (flagged as churny), or a `workflow_dispatch` of `tests.yml`.
- **Octave `control`/`signal` packages** are not guaranteed in a fresh container: Octave-based Welch/subspace oracles need a `pkg install` first.
- **`scripts/local-ci` prefers Octave** when both engines are on `PATH`: a LOCAL MATLAB-proper run needs `OCTAVE=/nonexistent scripts/local-ci matlab` or a direct `matlab -batch`.
- No job anywhere gives Octave-11 evidence until A10 lands.

### 10.2 Classification vocabulary

- **cloud** — fully developed and verified in a cloud session.
- **cloud-dev → PR-CI** — developed and Octave/Python-verified in the cloud; MATLAB-proper (and snap-Octave) confirmation comes from the PR's own CI jobs before merge; a LOCAL run is optional.
- **local** — cannot be meaningfully done without MATLAB/toolboxes on the author's machine (toolbox functions, engine-specific tolerances, interactive MATLAB-only behaviour).
- **ci-main** — canonical vector bytes from the canonical engine. Today that is the bot commit on `main` after merge; under A2 option (i) it becomes the PR MATLAB job's artifact, committed by the PR author before merge. Every "ci-main" cell below reads accordingly.
- **maintainer** — admin rights, secrets, credentials, or a `[decision]`; environment-independent.
